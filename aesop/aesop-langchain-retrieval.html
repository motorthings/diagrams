The LangChain Retrieval Layer

A customer asks a question. This layer turns it into a query, sends it to Databricks Vector Search, and hands back the closest documents. It is deliberately naive.

It applies no jurisdiction filter and no status filter. A superseded document, or a policy from the wrong state, can land in the answer. The retriever still records exactly what it pulled. That record is what the monitor reads.

What happens on one question

The path is short. Four steps from the customer's words to a written answer, and one more to the record that outlives it.

Step 1 · LangChain
Normalize, then build the query
Whitespace is collapsed. That is the only change. The retriever does not classify the question, does not re-scope it to a state, and does not set a filter. The query body has three fields: the text, the columns to return, and num_results.
Step 2 · Databricks
Ask for the nearest chunks
Vector Search ranks every chunk by embedding similarity and returns the top four. Nothing about the chunk's status, jurisdiction, or authority affects the ranking. Closest by meaning wins.
Step 3 · LangChain
Assemble the prompt
The chunks go into the prompt with their governance metadata printed above the text: status, jurisdiction, authority, effective_from. The model can see a document is superseded. The retriever still does not drop it.
Step 4 · Model
Write the answer
LLM answers from the passages only. If two passages conflict, it picks one and says which document it used. The answer is prose. It is not what the monitor grades.

No filter is the seeded failure, not a bug

The obvious fix is one line: add a filters_json clause so only current, in-state documents come back. Adding it deletes the demo.

The whole point of this layer is to fail the way a real deployment fails. A knowledge base goes stale, a jurisdiction filter never gets written, and the agent answers anyway. Fixing the retriever here removes the failures the monitor exists to catch.

So the retriever records what it did. Both filter fields are written as null. That null is not a missing value. It is the layer admitting that nothing was filtered.

filters: { jurisdiction: null, status: null } is the diagnosis. You do not have to guess why a stale document reached the answer. The trace says no status filter was applied. You do not have to guess why a Texas caller got a Minnesota policy. The trace says no jurisdiction filter was applied. The cause is written down, in the record, in the same shape every run.

What the trace carries

Every retrieved chunk is returned whole: its text plus the governance fields the index attached. The monitor reads these, never the answer prose.

The trace also carries filters, top_k, and the post-normalization query. Together they say what was asked, what came back, and what was filtered out. In this agent, nothing was.

One layer of two the monitor reads

The five checks run on the retrieved chunks' metadata, not on the sentence the model wrote. A judge that reads the answer is a second AI, with a second way to drift. This layer hands over facts instead.

The retriever produces the trace. The index attaches the governance fields to every chunk. The monitor compares those fields against fixed rules and returns the same finding every time.

How this layer feeds the AESOP monitor. Each interaction returns a retrieval block: the chunks, each with status, jurisdiction, operating company, authority, dates, and topic; plus the filters that were applied. The monitor's freshness, scope, authority, contradiction, and unclassified checks read exactly that block. Change a field name here and a check goes blind. The retriever is the supply line; the monitor is the reader.
